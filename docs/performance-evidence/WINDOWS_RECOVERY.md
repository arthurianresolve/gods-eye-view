## Confirmed fixture defect

The recovery harness reused one persistent Chrome profile across reopen stages. It opened a new tab with `browser.newPage()` for each stage, then called `browser.close()` while that tab was still open. On the next launch Chrome restored the old app tabs and the harness added another new tab. The stage target inventories show the app tabs accumulating, reaching four old app pages before the final stage. Some restored targets appeared after the initial target snapshot, so a single launch-time inventory was not sufficient.

The run at `8d1360c` exposed the defect in both renderer modes. The WebGL-only SwiftShader job reported all five stages passed, but it also restored uncontrolled app tabs and is invalid as clean recovery evidence. The full-driver SwiftShader job accumulated the same extra pages and failed the final workspace verification. Its instrumented `getParameter` phase took 86.6 seconds at stage two, 34.0 seconds at stage three, and 48.8 seconds at stage four. These are observed diagnostic durations, not a measured performance comparison: the WebGL-only and driver jobs ran on different CPU models, and the markers do not prove the Chromium engine mechanism behind the stalls.

Commit `fc67b90450625313414d36b986dbb2e54cdae2ad` addresses the fixture ownership defect without changing the app or renderer defaults. Each reopen requires exactly one initial `about:blank` page and reuses it. The harness rejects additional live page targets and page targets observed during the stage, requires the owned app page to be the sole page after boot and workspace verification, closes that page, verifies zero open pages, and requires graceful `browser.close()` before it reports a stage as passed. Unexpected restored pages are not closed to make a check pass. Browser-close fallback is limited to the process tree launched by this fixture.

The fix resolves this recovery-harness tab-ownership defect on the hosted Windows runner. It does not resolve or explain all renderer-query latency: in the full-driver job, the end-to-end renderer query took 23.697 to 59.627 seconds, while the instrumented `getParameter` phase took 23.075 to 59.030 seconds; boot took 31.968 to 46.235 seconds across stages. The exact Chromium/GPU-process mechanism remains unknown. The older `8d1360c` A/B jobs ran on different CPU models, so their timing differences are not a causal performance comparison. Recovery remains software-rendered fixture evidence, not hardware or GPU performance validation. At evidence-recording time, a full dev CI repeat containing this documentation commit has not yet run; broader S49 and S60 validation remains separate.

Supplemental local validation at the exact `fc67b90` code commit completed on Windows with Node 24.16.0: `npm test` exited successfully with 6,554 passing and zero failing tests. This was a no-browser unit suite, not a substitute for hosted recovery jobs.

The later full CI repeat at [run 37995293018](https://github.com/arthurianresolve/gods-eye-view/actions/runs/37995293018) also passed the original full-driver Windows recovery job [114039659519](https://github.com/arthurianresolve/gods-eye-view/actions/runs/37995293018/job/114039659519). All five stages passed with the unchanged renderer mode, zero extra page targets, and identical persisted workspace asset digests. This confirms the ownership fix in the broader CI run; the long query timings above remain unexplained and are not an app FPS or GPU-performance result.
