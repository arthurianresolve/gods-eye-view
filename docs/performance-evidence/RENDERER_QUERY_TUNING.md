# Windows renderer-query tuning experiment

The experiment added at `818105acea3e752b16f55a472f8aea3664285021` isolates two possible causes of slow Windows recovery queries: the SwiftShader backend and the time at which the fixture reads renderer identity. It makes no application or rendering-default changes. Its default push workflow runs two independent backend-only Windows jobs in `AB` and `BA` order. Manual dispatch can optionally select an early-query experiment using `ABC` and `CBA`:

| Variant            | Backend                 | Renderer query                                | Comparison purpose                |
| ------------------ | ----------------------- | --------------------------------------------- | --------------------------------- |
| `driver-late` (A)  | Full-driver SwiftShader | Existing query after boot                     | Control                           |
| `webgl-late` (B)   | WebGL-only SwiftShader  | Existing query after boot                     | Backend-only change versus A      |
| `driver-early` (C) | Full-driver SwiftShader | Query during Cesium's actual context creation | Query-timing-only change versus A |

Each job runs its reports sequentially on one Windows host with the same installed Chrome and five-stage fixture. `AB` runs A then B; `BA` reverses it. The optional `ABC` runs A, B, C; `CBA` runs C, B, A. Results are compared within each job, and timings from different Windows hosts are not pooled. Every report used in a comparison must match the workflow commit and pass all five unchanged recovery stages, preserve the declared workspace asset digest, one rendered feature, settings and exported workspace, and pass all page-ownership and closeout checks. Browser, OS, Node, host identity, viewport, and sequence metadata must be present and consistent within the job. A failed optional C report is recorded as incomparable and cannot make the overall sequence pass or invalidate a separately valid A/B comparison.

The early variant installs a one-shot hook before navigation and observes only the real canvas under Cesium's `.cesium-widget`. It calls the native `getContext` unchanged, reads the renderer on that returned context, restores the prototype hook immediately, and later verifies the canvas and original WebGL context against the live Cesium scene. It fails on missing or different context identity, context loss/restoration, missing renderer evidence, or failed cleanup. It creates no probe canvas and does not fall back to a late query. This is fixture-only instrumentation.

The comparison uses the median of the five per-stage **navigation-to-renderer-checkpoint critical paths**. Query-only duration is diagnostic and uses different clocks for early page-local query time and late host round-trip time; it is not the acceptance metric. A candidate must improve the median critical path by at least 20% versus A and must not have any per-stage regression greater than 10% in that sequence. Any within-sequence eligibility must be confirmed by the same candidate in the counterbalanced order. The validator reports each candidate independently and never combines timings across hosts.

The early-query candidate failed clean closeout in both optional-order jobs and is not accepted. In [CBA job 114049189731](https://github.com/arthurianresolve/gods-eye-view/actions/runs/37998106149/job/114049189731), its first recovery stage passed workspace, settings, asset, feature, and owned-page checks, but graceful browser close failed and required forced termination. The query measured 0.2 ms, while boot took 13.301 s and navigation-to-checkpoint took 13.308 s. In [ABC job 114049189456](https://github.com/arthurianresolve/gods-eye-view/actions/runs/37998106149/job/114049189456), the first stage passed cleanly with a 0.3 ms query, 65.187 s boot, and 65.270 s navigation-to-checkpoint. Stage two passed workspace and ownership checks but graceful browser close failed and required forced termination. Neither early report is valid for acceptance. The tiny page-query durations do not translate into an instant application start, and these failures do not establish that early querying caused the close failures. The [CBA raw report](renderer-query-818105a-cba-driver-early.json) and [ABC raw report](renderer-query-818105a-abc-driver-early.json) are retained.

In that ABC job, both `driver-late` and `webgl-late` independently passed all five stages with clean ownership, matching settings, one rendered feature, and identical persisted workspace asset digest `0de37a471d02bb57a555ac30082025624f55ddc576d312db772d9deb62f66fcc`. Their [raw reports](renderer-query-818105a-abc-driver-late.json) and [raw reports](renderer-query-818105a-abc-webgl-late.json) are retained for descriptive context. The ABC packet's original aggregate comparison is null because the early child failed, so these two reports do not replace complete counterbalanced backend-only AB/BA acceptance.

The first backend-only `AB` and counterbalanced `BA` runs at workflow commit `bdcd16487506a584865ed8b88f37451b5b8d9a79` each completed both reports successfully, but each original packet failed validation: the comparator expected digest `d41c5...`, while all four reports contained the actual fixture digest `0de37a471d02bb57a555ac30082025624f55ddc576d312db772d9deb62f66fcc`. The fixture text serialized by recovery was unchanged: UTF-8 `Persisted public investigation notes` followed by one LF. Commit `9b0b1bdea99764602cc754aaaad563c14150c7a1` corrected the checker to compute and share the digest from the same canonical fixture contract used by the recovery seeder. It did not modify fixture bytes or rerun any browser report.

The [AB offline re-evaluation](renderer-query-bdcd164-ab-reevaluation-9b0b1bd.json) applies that corrected validator to the unchanged AB reports and failed original packet. It finds the reports comparable, with the `webgl-late` median navigation-to-renderer-checkpoint critical path improving from 52,033 ms to 4,124 ms (92.1%) and no stage regression. The separately preserved [BA offline re-evaluation](renderer-query-bdcd164-ba-reevaluation-9b0b1bd.json) finds an improvement from 35,560 ms to 4,471 ms (87.4%), also with no stage regression. Both orders are within-host comparisons; their times are not pooled. Each sidecar records the source and validator commits and hashes of its three unchanged original inputs. Across both orders, all four original browser reports passed all five recovery stages (20 stage checks total), preserved matching settings and the same workspace fixture digest, and satisfied page ownership and graceful-close invariants. The corrected offline evaluator marks `webgl-late` eligible in both sequences. The original CI packets remain failed and unchanged; these are offline validator re-evaluations of their exact hashed inputs, not reruns. This evidence supports the Windows install-recovery CI job's WebGL-only SwiftShader setting with its existing explicit late renderer query, now configured in `ci.yml`. The full-driver diagnostic remains available, and application/global renderer defaults remain unchanged. This is not a GPU or application-performance claim.

These CI results guide only the Windows install-recovery fixture configuration. They do not measure application frame rate, GPU throughput, production rendering quality, or hardware performance. Application and global renderer defaults remain unchanged.
